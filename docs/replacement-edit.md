# 先新增、后删除的卡片修订（2.4.0）

用户已于2026-10-28明确选择先新增修订卡、再删除旧卡，允许文件ID改变。本流程不使用未经验证的原位内容写回。

1. 读取真实完整旧卡，构造保留全部未修改内容的完整新正文。`ima_edit_preview` 将候选全文、SHA-256、原文备份、新旧身份及两个固定请求号写入私有数据库；不改变ima内容。
2. 使用返回的 `replacement_plan.create_arguments` 原样调用 `ima_create_text_file`。服务端核对数据库候选、账号、同一知识库和父目录。未知只原号reconcile，不换号再上传。
3. 新增成功后调用计划中的 `ima_delete_preview`，取得具体删除hash，再调用独立 `ima_delete_execute`。删除前后端重新核对新卡的持久成功回执、实际目录和完整原文字节哈希；新增失败/未知、内容不符或旧卡漂移均不能删除。
4. 删除成功读回后，保存新旧ID映射，当前内容和位置指向新卡；历史发布的旧ID、审核、JSON、哈希、原文快照保留。未知只 `ima_delete_reconcile`，不重发删除。新增成功但旧卡未删除时如实保留两份，不报告修订完成。

支持1MiB以内UTF8 Markdown/TXT。治理卡片的文件内容只有标题和Markdown正文，entry_id、版本、分类、来源、哈希等元数据只保存在治理索引与私有数据库，不写进卡片正文。修订时由治理索引提供原身份与版本，版本递增后正文body_sha256重新计算，verification改为pending，不沿用旧审核结论；返回的body_sha256供调用方核对。私有数据库同时保留完整候选、原文备份、请求ID、原文及候选全文SHA-256、索引映射与审核历史。旧格式文件（标题加头部或尾部JSON代码块）仍可读取并按原规则递增版本，改写后按新格式输出。正文内JSON示例不得剥离；旧格式元数据损坏或身份不一致则停止，不能丢弃元数据以迁就操作。

新卡保留原父目录，文件名使用新版本或内容哈希修订后缀，避免同名覆盖。默认读取最新修订；显式指定历史发布版本时仍读历史原文。后续审核发布的previous_version从当前修订接续。

正式修订需要同一账号和隔离库绑定下，实际新增、原生删旧、全文哈希、备份与索引同步均通过；隔离验收独立于删除和移动验收。`same_id_edit_enabled=false`与`replacement_edit_enabled=true`可以同时成立。新旧ID不同是本方案的正常结果。

真实云端验收报告只能由实际回执生成。正式46篇本轮不批量改写。
