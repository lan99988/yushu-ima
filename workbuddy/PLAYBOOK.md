# 实操经验

安装看 [README](README.md)，规则细节看技能里的 `references/`。这一份只记录**实际跑通之后才明白的事**，每条都对应真实发生过的问题。

## 一、第一次跑通，按这个顺序

别一上来就动正式库。用隔离库把这五步走完，再碰真实资料：

1. 只读三连：`ima_knowledge_policy` → `ima_list_knowledge_bases` → `ima_list_directories`，确认真实能力与目录。
2. 写一张测试卡，正文两三百字即可。
3. 读回核对：字节数、开头是不是标题、有没有混进 JSON。
4. 修订一次，确认版本从 1.0 变成 1.1。
5. 删除，把核对推进到 `succeeded`，看四项校验是否全为 true。

这五步里任何一步含糊，都先别写真实内容。

## 二、怎么判断"真的成功了"

不看提示语，看四个可核对的事实：

| 检查项 | 合格标准 |
| --- | --- |
| 读回字节 | 与提交的基本一致，差额只应来自服务端追加的来源段 |
| 文件开头 | 直接是 `# 标题`，紧接正文 |
| 混入物 | 没有 ` ```json ` 围栏，没有单独的 `---` 分隔线 |
| 修订版本 | 递增（1.0 → 1.1），文件名是 `标题__v1.1.md` |

删除另有四项：同一原始身份、源已不存在、全库缺席、备份哈希核验。缺一项就是没删完。

## 三、会看到但不必慌的现象

| 现象 | 是什么 |
| --- | --- |
| `ima_edit_uses_explicit_create_then_delete` | 正常提示，说明走的是新建加删除，不是失败 |
| `verification_pending` | 删除后的分片扫描还没走完，沿原 `request_id` 继续核对 |
| `ima_openapi_readback_incomplete` | 预览阶段遇到索引滞后，**没有派发**，重试同一请求即可 |
| 修订后文件 ID 变了 | 正常。ima 没有原位改写，改就是新建一版再删旧版 |
| `md5_sum` 从空变成有值 | 服务端异步回填，不代表内容被改过 |

判断依据要落到这几种确定状态上，别看到"pending"就当失败去重发。

## 四、踩过并已修掉的坑

| 坑 | 根因 | 现在的行为 |
| --- | --- | --- |
| 启用统一入库后，替换编辑被拦成 `knowledge_ingest_required` | 门禁不认识替换登记表 | 登记过的替换创建放行，后续仍复核哈希与目录 |
| 旧卡明明没动，却报"卡片已改变" | 服务端把 `md5_sum` 异步补上 | 只允许"空 → 有值"这一项漂移 |
| 删除核对卡在几个目录不动 | 沿用旧的扫描游标 | 重建产物后一轮即可推完 |
| 文件名越改越长（`__修订_xxx__修订_yyy`） | 每次修订都追加后缀 | 统一成 `标题__vX.Y.md`，历史后缀自动剥掉 |
| 改了源码却没生效 | 本地桥加载 `dist/` 而不是 `worker/` | 改完必须 `npm run build` 再试 |
| 看起来"目录是空的" | 给 `ima_browse_knowledge` 多传了 `workspace` | 这类只读工具不接受该参数，多传会整条调用被拒 |

## 五、安全红线

**上传前必须扫一遍。** 仓库里最容易带出去的不是密码，是各种 ID：

- 知识库 ID（`ima_kb_*`）、原生数字 ID、目录 ID（`folder_*`）、媒体 ID（`markdown_cls1_*`）
- 知识库名称、账号名、邮箱
- 令牌、`.dev.vars` 任何内容
- 本机绝对路径

一条命令就能扫干净：

```text
grep -rnE "ima_kb_[A-Za-z0-9]{4,}|folder_[0-9]{10,}|markdown_cls1_[0-9a-f]{20,}" --include=*.md --include=*.json --include=*.mjs .
```

`.dev.vars` 必须留在 `.gitignore` 里，永远不要提交。

**已经推上去了怎么办：** 改文件 → `git commit --amend` 把改动并进那个提交 → `git push --force-with-lease` 覆盖远端。注意两点：被替换掉的旧提交在 GitHub 上可能短期仍能通过 URL 访问，要彻底清除只能等平台回收；如果别人已经拉过，强制推送会让他们的历史对不上。

## 六、动正式库之前

- 同一条链路先在隔离库跑通，尤其是删除和归并。
- 修改内容先给人看一遍再提交，不要直接改真实卡。
- 删除、批量归并要列出具体清单并取得针对清单的确认，"更新一下"不等于授权批量改。
- 内容没有实质变化就不要发起修订——格式好看不值得牺牲版本连续性。

## 七、给后续维护者的一句话

这套东西的原则是**每次用真实返回判断当前状态**：政策版本、门禁开关、目录树、验收证据，都要当次查询。文档、历史日志、截图、`serverInfo.version` 都不能替代一次真实调用。
