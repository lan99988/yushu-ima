# ChatGPT 网页端：个人答案库整理入库

## 目的与触发

这是问题驱动的个人生活答案库：围绕用户的困扰和疑问，保存从文章、视频文字稿、搜索、交流、AI 回答及亲身经历获得的答案；核查影响判断的关键说法，写明依据、适用条件和不确定性，随新证据及使用反馈更新。

用户要求“整理入库”“核实后入库”“保存这个答案”等时，ChatGPT 在当前网页对话主持完整流程。普通提问或讨论只检索和回答。用户已明确授权本批保存时，常规整理和保存直接执行；需要用户补材料或作价值选择时才提问。正文重要结论改写、跨分类、旧卡接管、新目录及多张既有卡归并移除沿用具体确认规则。每次录入或补充必须先读取[主卡规则](topic-cards.md)，只处理本次涉及的对象及旧卡。

插件负责私有持久化、版本、防重放和读回；ChatGPT 负责阅读、理解、搜索及核查。网页流程直接调用云端工具，不依赖本机程序、WorkBuddy、定时任务或第二个 ChatGPT 对话。视频链接本身不等于已有文字稿；没有可读取的完整材料时说明缺口，使用现有提取能力或请补充文字稿。

## 网页端直接写入与连续执行

用户在网页 ChatGPT 选择本插件并要求“保存到知识库”“整理入库”或“补充这张卡”后，在当前对话直接使用本插件的云端 MCP 工具完成流程。保存授权覆盖本批常规写入；多张既有卡归并移除、重大改写和新目录仍按具体方案确认。无需用户把材料再交给 Codex、本机脚本或另一个对话；只有实际缺少工具、连接或权限时才说明该缺口。

开始前读取真实政策、目标库绑定和 runtime.consolidation。已有卡归并须 enabled=true、acceptance_valid=true，且对象类型位于 supported_source_types；服务返回的有效证明才是依据。新建、已有卡更新及原样归档的入口遵守下方步骤和主卡规则。

归并采用分段执行。返回 verification_pending 或 unknown 时，保留完整原请求、预览及真实确认，在当前对话串行沿原号 reconcile；这会恢复已激活的事务，不能把它当作新执行或仅凭状态名称结束保存。依据 phase、progress.cleaned_count、scan.folders_checked、index.rows_checked 判断推进情况；有推进时继续，暂时无推进时适当间隔再核对，避免并发或密集重复调用。operation_in_progress 表示原事务受保护，等待并沿原号核对；不另起请求或手改锁。尚未激活的 preview 仍须按 execute 契约及实际授权执行，reconcile 不激活预览。

遇到权限、对象未登记、来源冲突、版本变化或需要具体确认等真实阻塞时，保留拟稿和事务身份，说明原因并请求必要信息。网页宿主若中断或达到工具限制，下次仍在同一网页对话接续原请求；不把本机执行器作为常规接续条件。只有成功收据、实际正文读回，以及相应归并清理和索引核验齐全后，才简报“已写入知识库”。

## 有序执行

1. **读材料和当前状态。** 使用 ima_knowledge_policy 及 ima_governance 的 bindings.get 核实政策和目标；涉及原生维护再读 ima_connection_status。阅读全文、实际查看相关图片，保留来源、作者、日期、段落/页码/时间戳等可得信息。聊天或附件本来就能读到全文时直接用，无法取得原件字节时不能假称已归档原件。
2. **确定对象与已有主卡。** 用拟定标题、核心词及别名在整个目标库同时执行 ima_knowledge_search 与 ima_search_knowledge，按游标取结果并通过 ima_knowledge_get / ima_read_media 读取候选正文、revision 和位置。登记未命中不代表库内没有；不能只查当前目录、标题或摘要。同一事物所有问题归一张完整主卡，例如吃法、选购都归《鱼油》，《蛋白粉》另建；概念只用词汇命名，独立且无法归入事物的问题用完整问句。存在 pending/unknown 先恢复原 payload；检索失败、正文不可读或身份歧义停预览。
3. **选择性核查。** 对影响结论的事实、数字、日期、因果、政策和高影响建议，实际搜索并打开出处，优先原始研究、官方资料或原作者。区分来源原话、作者观点、用户经验及 AI 综合；个人偏好和经验记录归属、时间、情境，不伪标事实核验。观点检查论据、前提、反例和适用条件；核查异议独立呈现，按 editorial-fidelity.md 保留原材料的重要论证和例子。搜索摘要、AI 自信和工具成功都不能当作已核实证据。无可用浏览能力或证据不足时如实标待核实/争议，不捏造链接。
4. **整合重写完整主卡。** 将现卡与新材料共同重写，先给当前答案，保留每个来源独特观点、论证、方法、例子、出处、分歧及带日期历史；同物不同问题作为正文小节，不另建重复专题或尾部补丁。材料提出方法或用户需要行动建议时写具体做法；按内容取舍栏目。一个主分类，交叉主题用标签及有依据的关系，优先复用现有目录。日期及事件截至日遵守知识2.0。
5. **分流预览与保存。** 双检索确认未命中的新卡用 ima_knowledge_ingest（policy_version=2.0.0，mode=organize，execute=false 后 true）；原样保存用 archive。已有卡的普通补充、修订或多卡归并必须走 ima_knowledge_consolidate（/knowledge action consolidate），先查实际 schema、runtime.consolidation、绑定、有效隔离验收 proof 及门禁；已确认对象范围为 registered_knowledge_object，纯原生未登记旧对象在接管能力及验收补齐前停预览并说明，不把原生命中当无命中新建。未就绪保留候选预览，不用旧 ingest 更新冒充单卡收拢。多张既有卡归并移除先展示具体清单、合并正文及重要差异，等待针对清单的真实确认；备份及主卡读回后才删除。事实核查证据与最终正文 hash 绑定，正文改变后重新计算与绑定；归并 confirmation 使用 {text,preview_hash,delete_media_ids} 对象，只填真实授权原文、服务当前预览 hash 和已确认的移除 ID，不捏造确认或扩大清单；其余字段只用实际契约。常规补充已有授权可复用，具体清单、重大改写及运行时审批仍各自生效。
6. **核对后交付。** 使用 ima_knowledge_get 和实际 media_id 的 ima_read_media 核对完整正文、分类、来源、原件及最终版本。已有卡还须核对备份、被替代条目移除、索引同步和仅一张当前可见主卡；新卡成功上传或单独 ingest 成功不证明归并完成。部分移除失败如实报告部分完成，不能删除新主卡做假回滚。archive 核对原件或笔记正文。unknown/verification_pending 各沿原入口、同一 request_id 与原完整 payload 仅加 reconcile=true 核对，不换号补发或迁移旧事务。交付只说明位置、问题、核查范围及缺口。

## 图片与未完成项

按 knowledge-2.md 处理相关原图及图下中文译文。图片显示和重开验收以本次服务真实状态及 protected proof 为准；没有有效验收时保留 blocked/verification_pending，不把上传成功说成图文完成，不为显示图片公开私有原图。不能静默丢图后声称整篇已完整入库。

## 完成标准

文本完成须同时有本次成功收据、稳定对象/版本及 ima 正文读回，保留来源原件的实际回执。已有卡更新还须满足[主卡完成标准](topic-cards.md#完成与恢复)，不能仅凭旧 ingest 收据报告已收拢。核查状态只覆盖真正查到的说法。可保存的观点、经验与灵感不必虚构事实证据；有疑点的事实在正文和核验状态中保留缺口。用可读的中文汇报，隐藏内部 JSON、令牌和服务配置。
