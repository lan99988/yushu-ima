# 主卡：同一事物的完整答案

本规则适用于每次 organize 录入、补充、改名、修订和归并。规则升级只规范本次涉及的对象与旧卡，不授权全库扫描改名、批量迁移、重写或删除。archive 保留原貌；旧 pending/prepared/unknown/verification_pending 沿原入口、原请求号、原完整 payload 和政策恢复，不因新规则改标题、重分卡或重派。

## 每次先双检索并读正文

1. 核实本次目标库、连接、认证、绑定、政策、实际能力、对应门禁和有效验收记录。插件版本、工具名称出现、历史日志及单项删除门禁开启都不能证明归并编排已验收；本次临时状态只写交付报告。
2. 用拟定标题、核心词和别名（包括同义词、常用称呼）在整个目标库同时做对象登记检索 ima_knowledge_search 和原生检索 ima_search_knowledge。搜索覆盖所有目录，不能只查当前文件夹或已登记条目；按真实游标继续分页并说明实际覆盖范围。每次补充也重新检索，不沿用旧结论。
3. 对可能同对象的候选用 ima_knowledge_get / ima_read_media 读取实际完整正文、当前版本、资源 ID、来源和位置。范围、对象、语境和内容共同决定身份；同名不能证明相同对象，登记未命中不能证明库内没有。
4. 任一检索失败、候选正文不可读、范围不足或归属歧义时，保留候选正文与预览，说明缺口；不能盲目新建、合并或删除。双检索完成且无同对象候选才进入新建；有同对象候选进入已有卡更新/归并。

## 标题与对象边界

- 同一具体事物的所有问题放在一张完整主卡。鱼油的吃法、剂量、选购、适用条件等都归《鱼油》，正文用小节承载；《蛋白粉》另建，不能因同属营养品并入鱼油。不按问题角度、来源篇数或内容长度另建同物专题卡。
- 概念标题只用词汇本身；具体事物用稳定名称。主卡标题不加“知识卡”“指南”“选购篇”等前后缀，不附日期、编号或修订版本。文章原题保留在来源及原件，不直接沿用为整理卡标题。目录的既有编号规则不变。
- 只有独立且无法归入具体事物的问题才建 question，并用完整问句，例如“怎样判断一条信息是否可靠？”。能归入事物的问题作为主卡小节。
- 不同概念、事物或独立事件仍分别建对象并建立有依据的关系。事件及时效信息保留真实日期、as_of 与时间线；日期在正文/元数据表达，不给概念标题加日期。
- 已有稳定 object.key 不因标题规范而随意改变。身份不清先预览，不用标题相似度替代正文判断。

## 整合重写与目录

读取现卡及可得原始材料，把新来源与旧内容整合重写成当前完整正文。当前答案在前，按需要保留解释、方法、例子、条件、分歧、仍待解决的问题及历史变化；不能仅在卡尾追加补丁或只保留最新观点。每份来源保留作者、原题、定位、日期、真实链接、独特主张与论证；原件独立保全，不覆盖。来源事实、作者观点、个人经验、AI 补充与核查异议分别标识，见[保真规则](editorial-fidelity.md)。

复用主卡已有合适目录；未命中新卡也优先复用目标库既有目录。一个主目录、多标签，不复制到多个目录。新目录仍须[本批具体路径确认](legacy-operations.md#多级目录每批先确认)，不能因规则升级重排旧目录。跨分类、旧卡接管或重大改写按[共享规范](knowledge-2.md#内容性质核查与重大改写)展示正文差异及依据，使用真实授权。

## 写入分流与归并能力

| 情形 | 入口及前提 |
|---|---|
| 双检索及候选正文比对后确认没有同对象卡 | 已验收统一服务 ima_knowledge_ingest，mode=organize，新对象 expected_version=0，policy_version=2.0.0 |
| 已有一张主卡的普通补充、改名、修订或内容更新 | ima_knowledge_consolidate，经 /knowledge action consolidate 新编排，连同被替代可见版本一起收拢 |
| 多张既有卡归并为一个主卡 | 同一 consolidate 编排，另须先展示具体清单并取得真实确认 |
| 明确原样存档 | 已验收统一 archive 入口，保留文本、图片及文件原貌，说明另存 |
| 旧已持久化未完成事务 | 原号、原完整 payload、原入口及原恢复契约，不迁移到新编排 |

ima_knowledge_consolidate 是归并入口，经 /knowledge action consolidate 调用；执行前必须实际读取当前 schema、runtime.consolidation 的真实能力、目标库绑定、归并与删除门禁及有效隔离端到端验收 proof。入口接入、工具出现或单独删除门禁开启均不代表已具备归并能力。runtime.consolidation 或 proof 缺失、无效、与当前实现/目标范围不匹配，或服务未就绪、未验收、返回 blocked/unavailable/unsupported 时，停在宿主预览；不冒称可用，不回退旧 ingest 更新，也不自行拼接低层上传/删除绕门禁。新建仍使用 ingest，不把所有保存强制改成归并。

归并对象须在实际能力声明及验收支持范围内；已确认的契约支持 registered_knowledge_object。仅存在于原生库、未登记的旧对象不属于该范围：停在预览，说明“旧卡尚未登记，当前归并入口不支持接管”，保留候选及完整合并稿；不能把原生命中当作未命中新建、伪造登记或改用旧 ingest 更新。只有后端随后明确提供并经本次能力查询及有效隔离 proof 证实支持原生对象接管，才按新增实际 schema 继续。

归并确认使用 confirmation 对象，字段为 text、preview_hash、delete_media_ids。text 只记录用户针对已展示方案的真实授权原文；preview_hash 使用服务当前预览返回的真实值；delete_media_ids 与该预览、用户确认的拟移除真实资源 ID 清单完全一致。不得由模型生成确认语、预览 hash 或扩充删除范围。版本前提、其他参数及恢复字段以实际工具 schema 与服务回执为准，不虚构成功字段。ingest 的 material 是单个对象，多来源须由经验证适配器分别保全原件，不臆造 materials 数组。正文审核与最终 hash 绑定，变更正文后重新核对；不能把旧审核移给新正文。

## 多卡归并确认与安全顺序

1. 先展示具体清单：目标库；拟保留主卡及其真实 ID、当前标题/位置/版本；每张拟移除卡的真实 ID、标题、目录及理由；合并后的完整正文、重要差异和来源保留方式。一次包含全部拟移除对象，不能只说“清理重复卡”。
2. 取得针对该清单的真实用户确认后才执行；保存授权、规则升级批准、自动审核通过或笼统“去重”不能冒充具体清单确认。已有授权确实覆盖同一份已展示清单时直接复用，不重复问；仍按 schema 提交 confirmation={text,preview_hash,delete_media_ids} 并准确绑定当前预览与实际 ID。清单、正文重要结论或范围变动，重新展示相应方案并确认；不伪造 confirmation。
3. 由经验证编排备份全部被替代旧正文、来源、ID、版本及位置并核对可读取；保存完整新主卡，取得持久成功收据，读取实际主卡正文与服务最终 hash/位置/版本。备份和主卡读回均通过后才移除已确认的替代项；任何失败、未知、旧卡漂移或门禁不符均停在相应阶段。
4. 单卡普通补充可复用已有具体更新授权，但也由同一编排管理备份、旧可见版本替换、读回与索引同步。发现其他既有卡时转入上述具体多卡清单确认，不借单卡更新授权删除它们。

## 完成与恢复

网页端分段归并在当前对话按[连续执行流程](web-intake.md#网页端直接写入与连续执行)恢复；verification_pending 有进度时继续沿原号核验，达到真实完成条件后再交付。

已有卡更新或多卡归并的完成条件必须全部满足：服务成功收据；备份可读；完整主卡实际正文读回且与最终回执一致；本次被替代条目已移除；索引和当前对象映射同步；整个目标库本次同对象检索及资源核对证明仅一个当前可见主卡。历史版本、来源原件与备份在非重复主卡的历史记录中保留，不以保留历史为由继续留下多份当前可见主卡。

旧 ingest 更新成功、上传成功、生成新 media_id、模型 pass 或登记更新都不能代替上述条件。删除未完成时报告“新主卡已保存、旧条目待移除/待核对”及具体清单，不报告单卡收拢完成，不删除新主卡做假回滚。任何事实核查结论仅覆盖实际核查范围。

unknown/verification_pending/超时沿同一入口、原 request_id、原完整 payload 按实际契约 reconcile；不换号、重传、换入口或自行重做删除。conflict 先只读核对当前版本和差异，不强写旧版本。新流程也不改造旧 pending/unknown 的 payload。确需进一步授权或能力不足时停预览并说明具体原因。

含图主卡继续遵守[原图片门禁](knowledge-2.md#图片录入规则)：原图及图下中文译文、protected admin 的真实截图及关闭重开证据、有效 proof 与实际正文读回均不可省略。归并成功、删除验收或文本完成均不能替代图片显示验收；不为显示私有图扩大公开范围。archive 原貌不受主卡改写影响。
